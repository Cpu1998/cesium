## 1. 先给结论：一帧 = 更新 → 画帧 → 收尾

把下面 §2 的长图先压缩成三句话，带着它再读时序图：

- **更新阶段**（prePasses→Passes→postUpdate）：所有数据侧的 `update` 在这里跑（Entity 同步、瓦片选择、命令收集），只产出 `DrawCommand` 列表，**不碰 GPU**；
- **画帧阶段**（preRender→render→postPassesUpdate 之前）：剔除、分 Pass、提交 WebGL，**这是最重的一段**；
- **收尾阶段**（postPassesUpdate→postRender）：派发网络请求、跑 afterRender 回调——把「会新增 Primitive 的用户回调」放在帧循环外的安全位置。

> 注意：**不画帧**（requestRenderMode 下 shouldRender=false）时，更新阶段照常跑、画帧阶段整体跳过。
> 所以「按需渲染」省的是画帧阶段，数据同步和请求派发从不缺席（§4）。

## 2. 一帧的完整旅程（总时序图）

先看全景。假设 `useDefaultRenderLoop = true`（默认），浏览器每次刷新（60Hz 屏≈16.7ms）触发一次回调：

```
浏览器 rAF(frameTime)
└─ CesiumWidget.js / startRenderLoop 内部 render(frameTime)
   ├─ 帧率节流：targetFrameRate 已设且距上帧 < interval → 直接 return（本帧不干活）
   ├─ widget.resize()        // canvas 尺寸/像素比变了才真正重设视锥
   └─ widget.render()        // ★一帧三拍（CesiumWidget.js / CesiumWidget.prototype.render）
      ├─ ① scene.initializeFrame()      // 着色器/纹理缓存每120帧GC、tween、相机控制器.update
      ├─ ② clock.tick()                 // 推进仿真时间 → 广播 onTick
      │    └─ CesiumWidget._onTick      // DataSourceDisplay.update：Entity→Primitive 差量同步（第3棒）
      └─ ③ scene.render(time)           // ★★Scene.js / Scene.prototype.render，一帧的主动脉
         │
         ├─ preUpdate 事件               // 外部改相机/数据的标准时机（ScreenSpaceEventHandler 等）
         ├─ checkForCameraUpdates        // 相机动过？→ cameraChanged（按需渲染脱脏条件之一）
         ├─ shouldRender 判定            // requestRenderMode 核心脏标记逻辑（§4）
         │
         ├─【更新阶段】prePassesUpdate(scene)
         │    ├─ primitives.prePassesUpdate  // Cesium3DTileset.prePassesUpdate：缓存淘汰等
         │    ├─ globe.update               // QuadtreePrimitive.update：影像集合 _update（第2棒）
         │    └─ 拾取缓存/版权更新
         │
         ├─【更新阶段】Passes 更新（primitives.show 时）
         │    ├─ updateMostDetailedRayPicks / updatePreloadPass / updatePreloadFlightPass
         │    │     // 都走 primitives.updateForPass：只加载不画（3D Tiles 预热）
         │    └─ 不画帧时：updateRequestRenderModeDeferCheckPass  // 唤醒检查（§4.3）
         │
         ├─ postUpdate 事件
         │
         ├─【画帧阶段】仅 shouldRender==true：
         │    ├─ preRender 事件 → render(scene)（Scene.js 私有函数）
         │    │    ├─ scene.updateFrameState()    // 重建帧状态：cullingVolume、occluder、清空 commandList
         │    │    ├─ fog.update + uniformState.update
         │    │    ├─ context.beginFrame / globe.beginFrame  // QuadtreePrimitive.beginFrame（第2棒）
         │    │    ├─ scene.updateEnvironment()   // 天空/大气/太阳/月亮
         │    │    └─ updateAndExecuteCommands(passState, bg)
         │    │         ├─ updateAndRenderPrimitives(scene)
         │    │         │    ├─ groundPrimitives.update / primitives.update
         │    │         │    │     // ★所有数据侧 update 在此被调：
         │    │         │    │     //   Cesium3DTileset.update（第4棒）、Billboard/Model/各 Primitive
         │    │         │    │     //   → 各自把 DrawCommand 推进 frameState.commandList
         │    │         │    ├─ globe.render → QuadtreePrimitive.render（第2棒）
         │    │         │    │     // selectTilesForRendering（SSE 选瓦片）→ addDrawCommandsForTile
         │    │         │    └─ updateShadowMaps
         │    │         ├─ view.createPotentiallyVisibleSet(scene)（View.js）
         │    │         │    // 逐命令：视锥剔除 isVisible + 地球遮挡 occlude → 算 near/far →
         │    │         │    //   分裂多视锥 updateFrustums → 按 Pass 装桶 insertIntoBin
         │    │         ├─ executeComputeCommands / executeShadowMapCastCommands
         │    │         └─ executeCommands(scene, passState)   // §5 详解
         │    │              // 逐视锥(远→近) × 逐 Pass：executeCommand→derivedCommands 变体切换
         │    │              //   →command.execute→Context.draw→gl.drawArrays/drawElements
         │    ├─ resolveFramebuffers    // 后处理（泛光/AA/HDR色调映射/选中高亮）合成到屏幕
         │    └─ globe.endFrame         // QuadtreePrimitive.endFrame：时间片加载队列（§5末）
         │
         ├─【收尾阶段】postPassesUpdate(scene)
         │    ├─ primitives.postPassesUpdate   // Cesium3DTileset.postPassesUpdate：缓存淘汰
         │    └─ ★RequestScheduler.update()   // 每帧末尾派发一批网络请求（§6）
         │
         ├─ callAfterRenderFunctions   // 瓦片就绪回调/进度事件（afterRender 队列统一执行）
         └─ postRender 事件            // CesiumWidget._postRender：zoomTo/跟踪实体收尾（第1棒）
```

三个阶段记住三句话就够了：更新阶段产命令不碰 GPU、画帧阶段别剔除分 Pass 提交、收尾阶段发请求跑回调——即 §1 的展开。

## 3. 帧率控制：rAF、targetFrameRate 与丢帧节流

[`CesiumWidget.js`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Widget/CesiumWidget.js) 的 [`startRenderLoop`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Widget/CesiumWidget.js#L61) 内部用一个闭包 [`render(frameTime)`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Widget/CesiumWidget.js#L65) 自我注册 `requestAnimationFrame`：

- **targetFrameRate 未设（默认）**：每个 rAF 回调都渲染，帧率跟随屏幕刷新率（60/120/144Hz）。
- **targetFrameRate 已设**（如 30）：计算 `interval = 1000 / targetFrameRate`，距上帧不足 interval 就只排下一帧、
  本帧不渲染（丢帧节流）。真正渲染后 `lastFrameTime = frameTime - (delta % interval)` 回退余数，
  **补偿累计漂移**——否则每帧都「多等一个 rAF」，长期平均帧率会明显低于目标值。

渲染抛异常时：`useDefaultRenderLoop` 置 false 停循环，弹错误面板（`_showRenderLoopErrors`）——
这就是为什么用户代码在事件回调里抛错常常表现为「地球冻住+红色弹窗」。

另一个常被混淆的概念：`maximumRenderTimeChange`（构造参数，挂在 Scene 上）与帧率无关，
它是 **requestRenderMode 下的时间脱脏阈值**（§4.2）。

## 4. requestRenderMode：脏标记按需渲染

### 4.1 原理：一组脏标记 + 一个判定

[`Scene.js`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js) 的 [`Scene.prototype.render`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L4670) 开头：

```js
let shouldRender =
  !this.requestRenderMode ||          // 非按需模式：恒 true
  this._renderRequested ||            // 显式 requestRender() 置脏
  cameraChanged ||                    // 相机动了（拖动/飞行）
  this._logDepthBufferDirty ||        // 对数深度开关变了
  this._hdrDirty ||                   // HDR 开关变了
  this.mode === SceneMode.MORPHING;   // 2D/3D 形变动画进行中
// 再补一条：仿真时间累计变化 > maximumRenderTimeChange 也算脏
```

`shouldRender = true` 时清掉全部脏标记、递增 `frameNumber`（各 Primitive 的每帧一次性标记都靠它）；
false 时跳过整个画帧阶段。**省的是 GPU 和大段 CPU 提交工作，因此移动端省电明显**。

谁会置脏（部分清单）：

- [`scene.requestRender()`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L4795)：用户显式调用（加 Entity、改样式、切图层之后）；
- 相机一切交互（相机控制器在 preUpdate 里改相机 → [View.checkForCameraUpdates](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/View.js#L131) 发现）；
- `Globe.tilesLoaded == false` 时每帧自动置脏（瓦片陆续到达，地表逐渐变清晰，Scene.js 的 [`render`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L4563) 私有函数末尾）；
- 瓦片就绪回调（[requestRenderAfterFrame](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L98) 工具、[updateRequestRenderModeDeferCheckPass](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L5156) 唤醒检查）。

### 4.2 与 shouldAnimate / timeline 的相互作用

按需渲染**不会**冻结时间轴：rAF 与 `clock.tick()` 每帧照常执行（[`CesiumWidget.prototype.render`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Widget/CesiumWidget.js#L1140)
的三拍结构不变）。于是：

- `shouldAnimate = true` 时仿真时间每帧都在走，`onTick` → [DataSourceDisplay.update](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/DataSources/DataSourceDisplay.js#L311) 每帧同步 Entity 位置——
  但**不重画**，除非时间变化超过 `maximumRenderTimeChange`（默认 0：任何时间变化都触发重画；设大它可在
  「时间在走但画面几乎不变」的场景进一步省帧，比如缓慢回放轨迹）。
- 反过来，`shouldAnimate = false` 且无交互时，Cesium 可以一帧都不画地「挂机」——这就是
  官方博客 *Improving Performance with Explicit Rendering* 推荐桌面静态场景开启它的原因。
- 时间轴 UI（widgets 包）拖动时会调 `clock.currentTime = ...`，随后请求重画。

### 4.3 deferCheck：不画帧的帧也要「望风」

按需模式下每个 rAF 仍会跑 [`updateRequestRenderModeDeferCheckPass`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L5156)：让 3D Tiles 检查那些
「暂不渲染、只加载」的请求是否就绪——就绪则 `requestRender()` 把渲染「叫醒」，避免按需模式下载吧
卡在低清画面。**更新阶段永远在跑**，这是理解 requestRenderMode 的关键：它裁剪的是画帧，不是世界。

## 5. executeCommands：从命令列表到 WebGL

### 5.1 剔除与分桶（[View.js](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/View.js) 的 [createPotentiallyVisibleSet](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/View.js#L285)）

`updateAndRenderPrimitives` 之后，`frameState.commandList` 里躺着本帧所有命令（几十到几千个）。
`View.createPotentiallyVisibleSet` 逐个过筛：

1. **视锥剔除**（Scene.js 的 [`Scene.prototype.isVisible`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L2146)）：命令的包围球在视锥 6 面外 → 丢弃；
   命令没包围球 → 只能按相机最坏 near/far 处理（不能误删）。
2. **遮挡剔除（一句话）**：`occlude=true` 的命令（典型是地球背面瓦片）再用椭球 `Occluder` 判一次——
   被地球挡住的直接不画；这也是为什么转到地球背面时前半球的瓦片不出现在命令流里。
3. **near/far 收集**：每个命令算出包围球沿视线的区间，汇总出全场景紧致 near/far。
4. **多视锥分裂**（[updateFrustums](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/View.js#L168)）：地球场景近远比可达 10⁶+，单个 24bit 深度缓冲扛不住
   （远处 z-fighting），按 near/far 拆成若干个连续视锥（`numFrustums`），逐个画。
5. **按 Pass 装桶**（[insertIntoBin](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/View.js#L236)）：命令的 `pass` 字段决定进哪个桶——
   `GLOBE / CESIUM_3D_TILE / OPAQUE / TRANSLUCENT / COMPUTE / OVERLAY / …`（枚举见 [Renderer/Pass.js](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/Pass.js)），
   同一命令可落多个视锥（`debugOverlappingFrustums` 位掩码）。

### 5.2 逐视锥逐 Pass 提交（Scene.js 的 [executeCommands](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L2796)）

外层循环**从远视锥到近视锥**（back to front），每个视锥先清深度，然后按固定 Pass 顺序 [`performPass`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L2845)：

```
GLOBE(地形) → TERRAIN_CLASSIFICATION → CESIUM_3D_TILE → 3DTile 分类
→ VOXELS → OPAQUE(不透明) → EDGES → SPLATS → TRANSLUCENT(半透明,远→近排序) → 3DTile 半透明分类
```

顺序背后的渲染常识：

- **不透明先画**：深度测试 early-z 让被挡像素跳过昂贵的片元着色；
- **半透明后画、且按包围球远→近排序**（[`performTranslucentPass`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L2604) → OIT 或排序执行）：
  alpha 混合顺序敏感，必须从后往前；
- **地形永远打底**，3D Tiles 分类（贴在模型上的矢量面）依赖模型的深度/模板。

每个命令最终经 Scene.js 的 [`executeCommand`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L2291)：按帧开关把命令换成 `derivedCommands` 变体
（对数深度 logDepth / HDR / pick 拾取色 / 阴影 receiveCommand），再 [`command.execute(context, passState)`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/DrawCommand.js#L316)。

### 5.3 提交 WebGL（Context.js 的 [Context.prototype.draw](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/Context.js#L1414)）

`Context.draw` = [beginDraw](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/Context.js#L1303)（绑 framebuffer、renderState、着色器程序、纹理）+ [continueDraw](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/Context.js#L1330)
（有 indexBuffer → `gl.drawElements`，否则 `gl.drawArrays`；instanced 命令走 instanced 变体）。
[`Context.endFrame`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/Context.js#L1442) 解绑所有 GL 状态。**DrawCommand 的意义就在这**（[Renderer/DrawCommand.js](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Renderer/DrawCommand.js)，简注）：
它是「一次 draw 调用的参数包」——数据侧（Primitive.update）只管生产参数包，Scene 只管排序分类，
Renderer 只管把参数包翻译成 gl 调用。三层互不认识，全靠这个对象解耦。

### 5.4 Globe 的三拍（QuadtreePrimitive 补注）

影像/地形侧的帧调度是 `beginFrame → render → endFrame` 三拍，分别由 `Scene.js` 的三处调用驱动：

| Scene 调用点 | QuadtreePrimitive 方法 | 干什么 |
|---|---|---|
| `render(scene)` 里 `globe.beginFrame` | [beginFrame](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/QuadtreePrimitive.js#L341) | 清加载队列、瓦片失效重建、LRU 帧标记 |
| `updateAndRenderPrimitives` 里 `globe.render` | [render](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/QuadtreePrimitive.js#L371) | [`selectTilesForRendering`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/QuadtreePrimitive.js#L522)（SSE 遍历、邻接判定）→ [`addDrawCommandsForTile`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/GlobeSurfaceTileProvider.js#L2528) 出命令 |

## 6. RequestScheduler：瓦片请求为什么不卡帧

**核心答案：网络请求天然异步（fetch），卡不卡取决于「发起与回调」怎么调度。** Cesium 的做法（[Core/RequestScheduler.js](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Core/RequestScheduler.js)）：

1. **统一入口**：影像瓦片、地形、tileset.json、b3dm、glTF…… 全部经 [`RequestScheduler.request`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Core/RequestScheduler.js#L405) 提交。
2. **双重限流**：全局并发 ≤ `maximumRequests`（默认 50），单服务器 ≤ `maximumRequestsPerServer`（默认 18）；
   超了直接返回 `undefined`，调用方下一帧再试（所以「排队」不占内存只占循环）。
3. **优先级堆**：待发请求进容量 20 的小顶堆，堆满时新请求可以把堆里最低优先级的**挤掉并取消**——
   快速拖动地球时，旧视角的瓦片请求就是这样被新视角抢占的。
4. **动态优先级**：每个请求带 `priorityFunction`，[`RequestScheduler.update`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Core/RequestScheduler.js#L296)（由 Scene.js 的 [postPassesUpdate](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L4548) 调用
   ，**每帧一次**）重算所有堆内请求的分数（瓦片按屏幕误差/距离/是否在主视锥打分）并重排。
5. **每帧填一批**：`update` 只把空闲槽位填满（弹出堆顶→[startRequest](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Core/RequestScheduler.js#L247)→真正 fetch），新到的请求下一帧再排。

于是「一帧的请求开销」= 维护一个 20 元素的堆 + 发起 ≤ 空闲槽数个 fetch——微秒级。
数据回来后 Promise 回调进入微任务队列，解码/建纹理发生在后续帧的更新阶段，依旧不阻塞当前帧。

另一个常被忽略的「不卡」保障是 **CPU 侧时间片**：[QuadtreePrimitive.processTileLoadQueue](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/QuadtreePrimitive.js#L1335) 每帧只花
约 5ms（`_loadQueueTimeSlice`）处理「已下载瓦片的装配」，Cesium3DTileset 的 [`updateTiles`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Cesium3DTileset.js#L3241) 同理——
CPU 重活被切成每帧一小片，宁可多花几帧加载，也不超预算掉帧。

## 7. 「Cesium 为什么卡/不卡」：单帧预算视角

把一帧 16.7ms（60Hz）当成预算表：

| 开销项 | 典型占用 | 说明 |
|---|---|---|
| 更新阶段（各 update） | 1–5ms | Entity 差量同步、瓦片选择、命令收集 |
| 剔除/分桶/排序 | <1ms | 几千个命令的纯 CPU 循环 |
| 提交 WebGL | 3–10ms | CPU 侧 gl 调用 + GPU 异步执行；draw call 太多时 CPU 先爆 |
| 请求派发 + afterRender | <1ms | §6 |
| **总预算超了 → 掉帧** | | |

掉帧常见元凶：draw call 数千+（合并批/3D Tiles 天然合批是解法）、超大几何单命令（GPU 顶点瓶颈）、
每帧 new 大量临时对象（GC 暂停——Cesium 源码里满地 `scratch` 复用对象就是为了这个）、
以及 MSAA/后处理档位过高。移动端首选项永远是：**开 requestRenderMode + 降 resolutionScale**。

（GC 与内存治理一句带过：[Scene.initializeFrame](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L4459) 每 120 帧做一次着色器/纹理缓存 GC；
`Cesium3DTileset.cacheBytes` 控制瓦片内存水位，详见 04 篇 §7。）

## 8. 调试入口与打点实验

- **内置帧率面板**：`viewer.scene.debugShowFramesPerSecond = true`（DOM 面板贴在 canvas 旁，
  按需渲染下会标 `throttled`；实现见 Scene.js 的 [`updateDebugShowFramesPerSecond`](https://github.com/Cpu1998/cesium/blob/study/1.145-annotated/packages/engine/Source/Scene/Scene.js#L4504)）。
- **瓦片调试**：`viewer.scene.globe.showWaterEffect` 之外更实用的是
  `viewer.scene.globe._surface._debug`（`tilesVisited / tilesRendered / tilesCulled / maxDepth`，
  `enableDebugOutput=true` 时每帧打印）；3D Tiles 用 `tileset.statistics` + `debugShowStatistics`。
- **请求调度观测**：`Cesium.RequestScheduler.debugShowStatistics = true`（活动请求归零时打印
  attempted/cancelled/failed 统计）；`Cesium.RequestScheduler.statistics` 可直接读。
- **命令级调试**：`scene.debugShowFrustums`（多视锥命中统计）、`scene.debugShowCommands`、
  `scene.debugCommandFilter`（过滤单个命令做二分定位）。
- **performance.now 打点实验**（建议动手）：

```js
viewer.scene.preUpdate.addEventListener(() => console.log("preUpdate", performance.now()));
viewer.scene.postUpdate.addEventListener(() => console.log("postUpdate", performance.now()));
viewer.scene.preRender.addEventListener(() => console.log("preRender", performance.now()));
viewer.scene.postRender.addEventListener(() => console.log("postRender", performance.now()));
// 对比相邻事件的时间差：postUpdate→preRender 若为 0，说明本帧被 shouldRender 跳过（按需模式）；
// preRender→postRender 的差值 ≈ 画帧阶段耗时（剔除+提交+同步等待），这是优化时的主表。
```

- **按需渲染体验**：`new Viewer(el, { requestRenderMode: true, maximumRenderTimeChange: Infinity })`
  然后拖一下地图、再松手——观察帧率面板归零（挂机不画）、一拖就满帧；把 `shouldAnimate` 打开对比。
